PROJECT:
ShadowWatch is an offline, explainable supervisory analytics platform for assessing SOC operational effectiveness.

It does NOT replace a SOC or SIEM and does NOT detect cyberattacks directly.

Its purpose is to analyze SOC operational evidence and identify:
- execution gaps
- expected-but-missing evidence ("negative space")
- suspicious investigation behaviour
- telemetry blind spots
- cross-source contradictions
- KPI gaming patterns
- weak SOC operational practices

The key concept is:

EXPECTED BEHAVIOUR
        ↓
Compare with
        ↓
OBSERVED EVIDENCE
        ↓
Find missing/unusual behaviour
        ↓
Generate explainable supervisory findings

NEXT DEVELOPMENT SECTION
NEGATIVE-SPACE ENGINE
==================================================

Now implement the first real negative-space detector:

R005 - TELEMETRY_BLIND_SPOT

Concept:

ShadowWatch should detect situations where telemetry normally exists for an asset but suddenly disappears or falls abnormally close to zero.

This is important because:

"No alert" does NOT necessarily mean "no attack".

If monitoring/logging disappeared, the SOC may simply have lost visibility.

Example:

Normal telemetry:

10:00 -> 130 events
11:00 -> 145 events
12:00 -> 137 events
13:00 -> 0 events
14:00 -> 0 events
15:00 -> 2 events

This should be considered a possible monitoring blind spot.

==================================================
R005 DESIGN REQUIREMENTS
==================================================

Create a separate service:

backend/services/negative_space_engine.py

Do NOT dump all analytics into rule_engine.py.

Implement a function such as:

detect_telemetry_blind_spots()

but adapt the exact implementation to the existing repository.

The detector should analyze telemetry separately for each:

entity_id + asset_id

and sort observations chronologically.

Use a historical baseline from earlier telemetry observations for that asset.

The detector should identify a significant unexpected telemetry drop.

Prefer a defensible approach such as:

baseline = rolling median / recent historical median

then compare current telemetry activity against the baseline.

Conceptually:

drop_ratio =
current_activity / baseline_activity

A candidate blind spot exists when:

baseline indicates that the asset normally produces meaningful telemetry

AND

current telemetry becomes zero or extremely low compared with that baseline

AND preferably the condition persists across multiple consecutive observations.

Do NOT hard-code a rule that simply says:

event_count == 0 -> anomaly

because naturally quiet assets may legitimately produce zero events.

Use historical behaviour.
